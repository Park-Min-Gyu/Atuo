# YL_AUTO v13 수정 내역 (2026-11-17, 해석 0/120 + Part2/3/5/6 메시 실패 대응)

## 받은 로그에서 확인된 것
1. **해석** : 메시가 된 모델은 전부 `TIME INCREMENT REQUIRED IS LESS THAN THE MINIMUM` / `TOO MANY ATTEMPTS`
   (비선형 발산)로 중단, `하중 케이스 0/15`, `extracted=False`.
   - 증분이 40~59 개까지 진행됐으므로 일부 스텝은 끝났을 가능성이 높은데, **중단된 ODB 에서 추출이 실패**해 0개로 집계됐다.
   - 통합 Job 은 스텝 하나가 발산하면 뒤 케이스가 전부 계산되지 않는다.
   - v11 은 스웨징을 -2 mm 부터 걸었다. 가장 가혹한 케이스가 맨 앞이라 거기서 발산하면 아무것도 못 얻는다.
   - **어느 스텝에서 왜 발산했는지는 이 로그만으로는 알 수 없다** (.sta / .msg 필요).
2. **메시 (Part2, 3, 5, 6)** : `solids after import : 0` = 면들이 꿰매지지 않은 STEP.
   표면 메시에 free edge(구멍)가 4~832개 남아 tetmesh 가 0개.

## 수정
### 해석
| # | 내용 |
|---|---|
| 1 | 스웨징 순서를 config 의 `swaging_mm` 순서(0, 1, 2, -1, -2)로. 순한 케이스부터 계산 |
| 2 | **발산 시 자동으로 이어서 계산** : `.sta` 로 어느 스텝이 발산했는지 찾아 그 케이스(스웨징 스텝이면 그 스웨징 값 전체)만 건너뛰고, 남은 케이스로 `<job>_r2`, `_r3` ... Job 을 만들어 계속 돌린다 |
| 3 | 로그에 `하중 스텝 SWp1p0_YP_LOAD 발산 (step time 0.400)` 처럼 **발산한 스텝 이름**을 표시, summary.csv 의 qc 열에도 기록 |
| 4 | `extract_odb.py` : 중단된 ODB 는 마지막 스텝에 결과가 없는데, 예전에는 그런 스텝이 하나라도 있으면 전체 추출을 포기했다 -> 그 스텝만 건너뜀. 추출 실패 시 `.extractlog` 내용을 로그에 표시 |

발산이 있으면 ODB 가 1개가 아니라 `_ALL.odb`, `_ALL_r2.odb` ... 로 늘어난다 (발산이 없으면 그대로 1개).

### 메시
| # | 내용 |
|---|---|
| 5 | HyperMesh : solid 가 0개면 면의 free edge 를 0.01 -> 0.05 -> 0.1 mm 로 꿰맴(`*selfstitchcombine`) |
| 6 | HyperMesh : 단순 메시 후 구멍이 남으면 절점 병합 허용오차를 요소크기의 2.5% -> 5% -> 10% 로 키워 가며 닫음. 단계마다 `check:` 줄 기록 |
| 7 | gmsh 예비 메셔 : solid 가 없으면 면을 꿰매서(sew, 최대 0.2 mm) solid 로 만든 뒤 메시 |

## 검증 범위
- 2~4 : 가짜 Abaqus 로 "하중 스텝 발산 / 원위치 스텝 발산 / 스웨징 스텝 발산" 세 경우 모두 이어서 계산되어 11/15 가 나오는 것 확인.
- 7 : 면만 있는 시험용 STEP 을 실제로 꿰매 메시함 (Tet 15,473개).
- 5, 6 : 모의 HyperMesh 로 문법/흐름만 확인. **`*selfstitchcombine` 인자는 HyperMesh 2019 에서 확인하지 못했다.**
  안 맞으면 hm_log.txt 에 `surface stitch ... 명령 실패` 로 남고 6번(절점 병합)으로 넘어간다.
- **발산 자체의 원인은 고치지 못했다.** 아래 파일이 있어야 볼 수 있다.

## 발산 원인을 보려면 필요한 파일
`auto_out/YL_logs_날짜.zip` (run_all.bat 이 자동으로 만든 것) 하나면 된다. 특히
