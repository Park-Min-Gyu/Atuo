## v27.4 (2026-11-28) : HyperMesh 에서 INP 가 안 열리던 문제 (`Fatal parsing error on line ...`)
- 증상 : 연구실 HyperMesh 2019 로 run 폴더 INP(NVH Update RHS DRT 모델)를 읽으면 `Fatal parsing error on line 7639 of ...` 같은 오류 196 개.
- 원인 : 해석용 INP 를 쓸 때 숫자를 Python 의 `.8g` 형식으로 써서 **0 에 아주 가까운 값이 지수 표기**로 나갔다.
  - 좌표 : 가운데 면(축 방향 0 mm) 근처 절점의 축 방향 좌표 -> `8e-06`, `-2.3e-05` (자동 헥사가 소수 6 자리로 쓴 거의 0 인 값)
  - 스웨징 변위 : OUTER 절점 중 축선(X = 0 또는 Z = 0) 근처 절점의 X/Z 변위 -> `1.5372949e-05`
  - `*Static` 의 최소 증분 -> `1e-08`
  HyperMesh 2019 의 Abaqus 읽기는 이런 줄을 읽지 못하고 그 절점/경계조건을 건너뛴다.
  **Abaqus 는 지수 표기를 읽으므로 해석 결과에는 영향이 없다** (해석이 안 된 모델은 메시 단계 실패 등 다른 이유).
  연구실 PC 에서 만든 LHS bushing 메시로 재현 : 메시 INP 439 줄 + 해석 INP 65 줄 = 504 줄.
  모델마다 수가 다르다 (축 방향 가운데 면이 원점에 있는 모델일수록 많음. SNUBBER 4 개는 0 줄이었음).
- 수정
  - INP 의 모든 실수를 **고정소수점**으로 쓴다 (항상 소수점이 있고 지수 표기와 `-0` 이 없음) : `19.`  `-22.986933`  `0.000008`  `0.00000001`.
    좌표와 변위는 소수 8 자리, 물성과 증분은 유효숫자 10 자리. nan/inf 가 있으면 INP 를 쓰지 않고 그 모델을 실패로 처리한다.
  - **INP 자동 검사** (`core/inp_check.py`) : build 단계가 INP 를 쓴 직후 검사해서 `run/<모델>_inpcheck.txt` 에 쓴다.
    Abaqus 도 못 읽을 오류(nan, 번호 중복, 없는 절점/세트 참조, 요소 절점 수, 256 자 넘는 줄 등)가 있으면 해석 전에 멈추고 이유를 로그에 남긴다.
    정상이면 로그의 build OK 줄 끝에 `INP 검사 OK (Abaqus/HyperMesh 형식)` 이 붙는다.
  - **`check_inp.py`** (예전 INP 검사와 고치기)
    | 명령 | 하는 일 |
    |---|---|
    | `python check_inp.py` | auto_out 아래 모든 INP 검사 |
    | `python check_inp.py --fix` | 지수 표기 숫자를 고정소수점으로 바꿔 다시 저장 (값은 그대로 -> 끝난 해석은 다시 돌리지 않음) |
    | `python check_inp.py <INP> 7639 7641` | HyperMesh 가 오류를 낸 줄의 내용과 블록 보기 (*Include 한 메시 INP 의 같은 줄도 같이 보여 줌) |
  - v27.4 로 다시 실행하면 build 단계가 INP 를 새로 쓴다. 예전 INP 와 **숫자 표기만 다르고 값이 같으면** (차이 1e-6 이하)
    해석 상태 파일의 입력 지문을 갱신해서 **이미 끝난 해석은 다시 돌리지 않는다** (로그 : `INP 숫자 표기만 바뀜 (값은 같음) -> 이전 해석 결과를 그대로 씀`).
  - `collect_logs.py` 가 모든 모델의 INP 검사 요약(`inp_check_summary.txt`)을 같이 묶는다.
- 확인
  - LHS bushing, RR GEARCASE (연구실 PC 의 자동 헥사 메시), SNUBBER CASE03 : 새 INP 의 지수 표기 0 줄, `-0` 0 개, INP 검사 통과.
  - SNUBBER CASE03 를 CalculiX 로 다시 해석 : 2 mm 반력 X 387.5492 / Y 198.6108 / Z 776.0352 N (이전 387.5492 / 198.6105 / 776.0351 N, 같음).
  - 예전 형식 INP 에 `check_inp.py --fix` : 504 줄 고침, 다시 검사 0 줄, 해석 상태 파일 지문 갱신 확인.
  - 예전 형식 INP 가 있는 run 폴더에서 v27.4 build : `INP 숫자 표기만 바뀜 (값은 같음) -> 이전 해석 결과를 그대로 씀`.

  - 파이프라인이 **'모든 모델 메시 -> 그다음 모든 모델 해석'** 순서였다. 테트라 때는 메시가 모델당 몇 분이라 바로 해석으로 넘어갔지만,
    자동 헥사는 모델당 수 분~수십 분이고 실패하는 모델은 최대 7 번 시도하므로 메시 단계만 몇 시간 걸린다.
    그동안 Abaqus 는 하나도 시작하지 않고, 그 전에 창을 닫으면 해석이 전혀 없다.
  - 자동 헥사가 실패한 모델은 실행할 때마다 처음부터 다시 시도했다 (같은 CAD, 같은 코드면 결과도 같음).
  - **D 드라이브는 원인이 아니다.** RHS DRT 는 D:\YL_AUTO 에서 Abaqus 가 실제로 돌아 ODB 를 만들었다. `run_all.bat` 도 자기 폴더 기준으로 실행한다.
